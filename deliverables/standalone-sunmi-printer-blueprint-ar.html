وثيقة مستقلة — لا تحتوي أي ربط بالمشروع المرجعي

مخطط بناء تطبيق طابعة طلبات Sunmi V3

مواصفات كاملة لبناء تطبيق Android مستقل لإدارة طلبات مطعم، التنبيه المستمر، قبول الطلب، الطباعة الحرارية التلقائية، منع التكرار، وإسناد مندوب التوصيل.

1. شرط الاستقلال الكامل

قاعدة إلزامية: المشروع الجديد لا يستخدم أي رابط API أو قاعدة بيانات أو package ID أو Expo project ID أو مفاتيح توقيع أو صور أو أسرار من أي مشروع آخر.
  • أنشئ مستودعًا ومجلد مشروع جديدين.
  • اختر اسم تطبيق وslug وAndroid package مختلفين، مثال: com.NEW_BRAND.printer.
  • أنشئ EAS Project وAndroid Keystore جديدين.
  • أنشئ API وقاعدة PostgreSQL مستقلين.
  • استخدم متغيرًا جديدًا مثل EXPO_PUBLIC_API_BASE_URL ولا تضع رابطًا ثابتًا في الكود.
  • لا تنسخ ملفات .env أو credentials أو service accounts.
  • أضف فحص تشغيل يمنع التطبيق من البدء إذا بقيت قيمة placeholder أو ظهر رابط مشروع آخر.

2. النتيجة المطلوبة

تطبيق Android يعمل على جهاز Sunmi V3 ويقوم بالآتي:

  1. يتصل بالـAPI المستقل ويجلب الطلبات كل 5 ثوانٍ وعند فتح التطبيق أو عودته للمقدمة.
  2. عند وجود طلب pending اليوم: يشغّل صوتًا متكررًا واهتزازًا مستمرًا.
  3. زر «قبول وتجهيز» يوقف تنبيه ذلك الطلب فورًا ثم يطلب تغيير حالته إلى preparing.
  4. إذا فشل تغيير الحالة يعود التنبيه. إذا نجح لا يعود التنبيه.
  5. أي طلب preparing غير مطبوع يدخل طابور الطباعة ويُطبع مرة واحدة فقط.
  6. بعد قبول طلب توصيل، يقرأ إعداد الإسناد: تلقائيًا يختار مندوبًا متاحًا، ويدويًا يعرض قائمة.
  7. طلبات pickup لا تُسند إلى مندوب.
  8. يتيح إدارة الطلبات، القائمة، ساعات العمل، إعدادات الصوت والدفع، والسجل.

4. التقنية المقترحة

  • Expo + React Native + TypeScript + Expo Router.
  • React Query لإدارة بيانات الخادم.
  • Express + TypeScript للـAPI.
  • PostgreSQL + Drizzle ORM أو ORM مكافئ.
  • AsyncStorage أو SQLite لسجل الطباعة المحلي.
  • @mitsuharu/react-native-sunmi-printer-library أو مكتبة Sunmi متوافقة ومختبرة.
  • expo-audio للصوت وReact Native Vibration للاهتزاز.
  • EAS Build بملف APK داخلي للتثبيت المباشر.
مكتبة Sunmi native لا تعمل داخل Expo Go أو الويب. يجب استخدام Development Build أو APK حقيقي على جهاز Sunmi.

5. حالات الطلب

pending
  └── قبول المطعم → preparing
        ├── pickup: طباعة ثم ready → done
        └── delivery: طباعة + إسناد مندوب
              └── ready → out_for_delivery → done

يمكن الانتقال إلى cancelled فقط حسب سياسة واضحة ومتحقق منها في الخادم.

يجب أن يملك الخادم مصفوفة انتقالات معتمدة؛ لا يسمح للعميل بإرسال أي انتقال عشوائي. الأسعار والإجماليات وحالة التوفر تُحسب وتُتحقق في الخادم.

6. التنبيه الصوتي والاهتزاز

  1. حمّل ملف صوت محلي داخل APK، ولا تعتمد على رابط شبكة.
  2. ابنِ Set للطلبات pending التي تم إسكاتها مؤقتًا.
  3. إذا وجد طلب pending غير مسكت: شغّل الصوت loop واهتزازًا بنمط متكرر.
  4. عند ضغط قبول: أضف ID إلى Set قبل طلب الشبكة، فيتوقف فورًا.
  5. عند فشل PATCH: احذف ID من Set ليعود التنبيه.
  6. عند نجاح PATCH أو اختفاء الطلب من pending: نظف ID نهائيًا.
  7. عند عدم وجود أي طلب pending: أوقف الصوت، أعده للبداية، وألغ الاهتزاز.
لا توقف التنبيه بسبب فتح الشاشة فقط. التوقف مرتبط بقبول ناجح، إلغاء الطلب، أو خروجه الفعلي من pending.

7. الطباعة التلقائية ومنع التكرار

خوارزمية الطباعة

  1. اجلب طلبات اليوم.
  2. رشّح الحالة preparing.
  3. استبعد IDs الموجودة في سجل printedOrderIds.
  4. رتب من الأقدم إلى الأحدث.
  5. اطبع طلبًا واحدًا فقط في كل مرة.
  6. بعد نجاح كامل تسلسل Sunmi، احفظ ID محليًا.
  7. عند الفشل لا تحفظ ID، وانتظر 30 ثانية قبل إعادة المحاولة.

منع التكرار

  • سجل محلي دائم في AsyncStorage/SQLite يبقى بعد إعادة تشغيل التطبيق والجهاز.
  • Set للطلبات قيد الطباعة يمنع بدء عمليتين لنفس الطلب.
  • لا تكتب «مطبوع» قبل نجاح آخر أمر feed/cut أو اكتمال المكتبة.
  • لأكثر من طابعة: أضف جدول خادم print_receipts ومفتاح unique على (order_id, device_id).
  • إعادة الطباعة اليدوية تحتاج تأكيدًا واضحًا وتسجل السبب.

8. تصميم الإيصال

  1. اسم المطعم في المنتصف وبخط عريض.
  2. رقم الطلب اليومي والتاريخ والوقت.
  3. نوع الطلب: توصيل أو استلام شخصي.
  4. بيانات العميل والعنوان للتوصيل.
  5. جدول أصناف مناسب لعرض 72/80mm: الصنف، الكمية، السعر.
  6. الإضافات والملاحظات تحت الصنف.
  7. المجموع الفرعي، رسوم التوصيل، الخصم، ثم الإجمالي بخط عريض.
  8. طريقة الدفع وملاحظات الطلب.
  9. Feed كافٍ في نهاية الورقة.

احتفظ بالمال في قاعدة البيانات بوحدة هللة/سنت كعدد صحيح. حوّله إلى ريال فقط عند العرض والطباعة.

9. إسناد المندوب

تعريف المندوب المتاح

  • active = true
  • is_online = true
  • لا يملك assignment نشطًا بحالة assigned أو picked_up لطلب غير منتهٍ.
  • إذا توفر GPS حديث، يرتب حسب الأقرب للمطعم؛ وإلا يوضع بعد من يملك موقعًا صالحًا.

التدفق

  1. يتم أولًا قبول الطلب وتحويله إلى preparing.
  2. إذا كان pickup ينتهي التدفق دون إسناد.
  3. اقرأ drivers_auto_assign.
  4. إذا true: أرسل POST دون driverId.
  5. إذا false: اجلب المتاحين وافتح Modal، ثم أرسل driverId المختار.
  6. فشل الإسناد لا يعيد الطلب إلى pending ولا يعيد صوت الطلب.
شرط transaction: اقفل عملية الإسناد، أعد فحص أن الطلب preparing وأن المندوب ما زال متاحًا، ثم أنشئ assignment واحدًا فقط. لا تغيّر حالة الطلب داخل endpoint الإسناد.

14. اختبارات القبول الإلزامية

  1. طلب pending جديد يشغل الصوت والاهتزاز حتى القبول.
  2. فشل قبول الطلب يعيد التنبيه.
  3. نجاح القبول يحول إلى preparing ويطبع مرة واحدة.
  4. تكرار polling عشرات المرات لا يعيد الطباعة.
  5. إغلاق وفتح التطبيق أو إعادة تشغيل الجهاز لا يعيد طباعة الطلب.
  6. نفاد الورق لا يسجل الطلب كمطبوع، ويعيد المحاولة بعد إصلاح الطابعة.
  7. طلبات pickup لا تُسند لمندوب.
  8. الوضع التلقائي يختار مندوبًا متاحًا واحدًا فقط.
  9. الوضع اليدوي يعرض المتاحين ويمنع المندوب المشغول.
  10. الإسناد لا يغيّر حالة preparing.
  11. اختبار انقطاع الشبكة وعودتها، وقفل الشاشة، والخروج للمقدمة.
  12. اختبار إيصال عربي طويل، إضافات كثيرة، ملاحظات، ورسوم وخصم.
  13. التأكد أن APK يتصل فقط بالـAPI الجديد المستقل.
  14. فحص APK النهائي: package وversionCode والتوقيع تخص المشروع الجديد.

15. نص جاهز لإعطائه لوكيل المشروع الثاني

ابنِ من الصفر تطبيق Android مستقل لطابعة Sunmi V3 لإدارة طلبات مطعم.

قواعد صارمة:
1. لا تربط أو تستورد أي كود أو API أو قاعدة بيانات أو أسرار أو package ID أو Expo project ID أو keystore من أي مشروع سابق.
2. أنشئ API وPostgreSQL وEAS Project وAndroid package وتوقيعًا جديدًا.
3. اجعل رابط API متغير بيئة إلزاميًا، وافشل صراحة إذا كان مفقودًا أو placeholder.
4. لا تستخدم بيانات وهمية في النسخة النهائية.

الوظائف:
- واجهة عربية RTL بتبويبات: جديد، قيد التحضير، الوجبة جاهزة، الاسترداد.
- قائمة جانبية: طلبات اليوم، الطلبات السابقة، الأصناف، ساعات العمل، الإعدادات، تشخيص الطابعة.
- polling للطلبات كل 5 ثوانٍ وعند عودة التطبيق للمقدمة.
- صوت loop واهتزاز مستمر لكل طلب pending حتى قبول ناجح.
- زر قبول وتجهيز: يسكت التنبيه فورًا، PATCH إلى preparing، ويعيد التنبيه فقط إذا فشل PATCH.
- طباعة تلقائية عبر مكتبة Sunmi للطلبات preparing، الأقدم أولًا، عملية واحدة في كل مرة.
- سجل محلي دائم للطلبات المطبوعة، ولا يُسجل ID إلا بعد اكتمال الطباعة بنجاح.
- retry بعد 30 ثانية عند فشل الطابعة، دون طباعة متزامنة أو مكررة.
- إيصال عربي: رأس المطعم، رقم الطلب، بيانات العميل، الأصناف، الإضافات، الرسوم، الخصم، الإجمالي، الدفع والملاحظات.
- إدارة توفر الأصناف، ساعات استقبال الطلبات، أصوات التنبيه ووسائل الدفع.
- بعد قبول delivery: اقرأ drivers_auto_assign. إذا true عيّن تلقائيًا، وإذا false اعرض المندوبين المتاحين.
- pickup لا يفتح اختيار مندوب ولا ينشئ assignment.
- endpoint الإسناد transactional وidempotent، يعيد فحص preparing وتوفر المندوب ولا يغير حالة الطلب.
- الأخطاء JSON عربية ومتسقة. في العميل اقرأ response body مرة واحدة فقط.

التقنية:
Expo/React Native/TypeScript/Expo Router/React Query، Express/TypeScript، PostgreSQL، وEAS APK داخلي.

قبل التسليم:
- شغّل TypeScript والفحوصات.
- اختبر على Sunmi V3 الحقيقي.
- أثبت أن polling لا يكرر الطباعة.
- أثبت أن restart لا يكرر الطباعة.
- اختبر paper-out والشبكة والتنبيه وpickup والتعيين التلقائي واليدوي.
- أعطني APK ورابط build وSHA-256 وقائمة المتغيرات المطلوبة دون كشف أي سر.

16. قائمة المعلومات التي يجب توفيرها للمشروع الجديد

  • اسم المطعم الجديد وشعاره وألوانه.
  • رابط API الجديد بعد نشره.
  • منطقة الوقت والعملة والضريبة.
  • عرض ورق الطابعة وطراز Sunmi الدقيق.
  • سياسة حالات الطلب والإلغاء والاسترداد.
  • هل توجد طابعة واحدة أم عدة أجهزة؟
  • بيانات EAS/Expo الخاصة بالمشروع الجديد من خلال Secrets، لا داخل المحادثة أو الكود.
  • حساب قاعدة البيانات وخدمات الإشعارات الجديدة من خلال Secrets.
هذه الوثيقة مواصفات عامة مستقلة. القيم المكتوبة بأحرف كبيرة placeholders ويجب استبدالها بقيم المشروع الجديد. لا تحتوي الوثيقة على أسرار أو روابط إنتاج أو معرفات أو بيانات من المشروع المرجعي.
